# ablation-03 节点级缓存与断点恢复实施计划

## 通俗解释：究竟发生了什么

- **一句话说明：** 当前分析会把若干步骤连续做完后才统一保存结果；如果后面的步骤失败，前面已经完成的工作可能需要重做。
- **生活类比：** 这像填写一份很长的表格，只有全部填完才保存。即使前九页已经完成，第十页出错后再次打开仍可能从第一页开始。
- **对应到本问题：** 表格的每一页对应 retrieval、readout、learning curve、decoder 等计算节点；保存对应把结果和计算条件写入可复用的 RDS 缓存。
- **改变前后：** 现在若 decoder 阶段失败，较早完成的 readout 仍可能重算；改进后，每个高耗时节点完成即形成可靠检查点，重跑只继续缺失或已经失效的节点。

## 专业判断：问题在哪里

- **当前现象：** `ablation.R` 已经为 Direct 特征、精确 geometry 和 cohort-scaling 拟合提供缓存，但 retrieval、readout、learning curve 和 decoder 主要在表示流程末尾集中落盘。它们不是可独立恢复的计算节点。
- **影响范围：** 当前 `ablation-03` 规模较小，发生问题的概率和单次重算成本都可接受，因此本项属于低优先级工程改进。未来扩大样本、重复次数或调参范围后，中途失败和反复修改下游分析会显著放大重算成本。
- **已知原因：** 表示分析仍按一次性函数调用组织，阶段凭据用于发现陈旧或混合产物，但不能恢复函数内部已经完成的节点。部分热点缓存已经证明内容键复用方案可行，可以在此基础上扩展，而不需要改写统计方法。

## 优先级与启动条件

本计划暂不实施，也不影响当前正在运行的分析。满足以下任一条件时再启动：

- 单次表示分析耗时增长到失败后不愿完整重跑的程度；
- 同一份表示输入需要反复调整下游参数；
- 实际出现进程中断、内存错误或机器重启导致的明显重复计算；
- `ablation()` 被用于更大的数据集或批量实验。

## 要达到什么目标

- **完成后的变化：** 相同输入、参数和算法版本下，重新运行会复用已经完成的高耗时节点；只重新计算受变化影响的节点及其下游。
- **可靠性要求：** 中断不能留下看似完整但实际损坏的缓存；缓存损坏、版本不匹配或输入改变时必须安全地视为未命中。
- **兼容性要求：** 保持 `ablation()` 的现有统计行为、返回结构和面向报告的正式产物名称；无缓存运行与首次缓存运行应得到等价结果。
- **不在本次处理范围：** 不改变统计方法、样本资格、默认参数或随机种子；不引入分布式任务系统、通用工作流框架、数据库或远程缓存；不为低成本汇总结果建立不必要的缓存层。

## 改进方向

### 把高耗时计算拆成可恢复节点

为 retrieval（包括 anchor retrieval）、readout、learning curve 和 decoder 定义独立的输入契约、输出契约与缓存身份。节点只依赖实际需要的上游数据和参数，某个参数变化不应让无关节点失效。

对使用者而言，这意味着调整 learning curve 参数时，已经完成且条件未变化的 retrieval 不必再次计算。

### 使用内容键和多版本缓存

每个节点的缓存键至少绑定实际输入内容、相关配置、seed、缓存 schema 和算法修订标识。缓存按节点和内容键分开保存，避免一次新参数运行覆盖旧参数的可复用结果。算法修订标识应保持明确、稳定；普通文档变化不应使科学计算缓存全部失效。

对使用者而言，这意味着在参数 A 和参数 B 之间来回比较时，可以分别复用两套已完成结果。

### 原子保存并明确运行状态

复用现有原子 RDS 保存能力：先写临时文件，完整写入后再替换目标。表示阶段开始时记录 `running` 状态，成功提交所有正式结果和最终凭据后改为 `complete`；异常退出保留为可识别的未完成状态。报告和下游阶段只能接受 `complete` 的正式结果，但节点缓存可以用于恢复下一次运行。

对使用者而言，这意味着进程被终止时，半写入文件不会被误认为有效结果，旧结果和本轮未完成结果也不会混在一起。

### 保持正式结果与恢复缓存分离

节点缓存只负责节省计算，现有 `manifest.rds`、`retrieval.rds`、`readout.rds` 等仍是面向报告和审计的正式产物。只有整轮运行完成后，才原子更新正式产物和阶段凭据。缓存命中、未命中及失效原因写入 manifest 或简洁审计表，便于确认本轮究竟复用了什么。

对使用者而言，这意味着报告接口无需改变，同时可以清楚区分“用于恢复的中间缓存”和“已经完成并可用于文章的结果”。

## 实施范围与顺序

1. 先固定四类节点的依赖、内容键和输出契约，并为现有热点缓存补齐一致的错误处理约定。
2. 再接入节点级读取与原子保存，优先覆盖 readout、learning curve 和 decoder，随后覆盖 retrieval 与 anchor retrieval。
3. 增加阶段运行状态与最终提交边界，使下游分析和报告不会接受未完成批次。
4. 最后补充缓存命中审计、回归测试和 `ablation-03` 运行说明；确认无缓存、首次运行和恢复运行的科学结果一致。

## 如何确认完成

- 相同输入和配置连续运行两次，第二次明确命中各节点缓存，且不会再次调用对应的高耗时计算。
- 人为在 retrieval 完成后、decoder 完成前中断流程，再次运行能够复用已经完成的节点并继续剩余工作。
- 只修改 learning curve 参数时，仅 learning curve 及确有依赖的下游结果失效；retrieval 和无关 readout 缓存保持可用。
- 修改样本、表示矩阵、相关参数、seed 或算法修订标识时，对应节点必须缓存未命中。
- 截断或替换一个缓存文件后，流程能识别损坏并安全重算，不把损坏文件提升为正式结果。
- 运行状态不是 `complete` 时，R Markdown 报告和下游阶段明确拒绝读取本轮正式结果。
- 禁用缓存、首次计算和缓存恢复所得的正式 RDS 在允许的数值容差内一致，样本顺序、字段结构和审计信息符合现有契约。
- Windows R 4.3.1 下验证原子替换、进程中断后的恢复以及现有 Direct 缓存回归测试。

## 风险与待确认事项

- **存储增长：** 多版本缓存会占用更多磁盘。初版不自动删除缓存，避免误删昂贵结果；真正实施前确认保留策略和人工清理入口。
- **失效过宽或过窄：** 内容键绑定过宽会造成无意义重算，绑定不足会复用错误结果。实现时应为每个节点单独列出依赖，并用参数变更测试验证边界。
- **随机性：** 所有随机节点必须把 seed 纳入缓存身份，并确认并行执行不会改变既有可复现性约定。
- **兼容性：** 节点缓存是内部实现细节，不应改变公开返回对象和报告所读取的正式文件。必要的 schema 变化只记录在 `[Unreleased]`，不自行修改项目版本号。
- **当前运行：** 本计划不得用于修改或接管 2026-09-17 正在运行的 `ablation-03` 进程；实施应从一次独立、可控的后续任务开始。
