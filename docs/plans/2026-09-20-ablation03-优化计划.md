# ablation-03 稳定性与运行边界优化计划

## 通俗解释：究竟发生了什么

这次运行暴露的不是单一慢步骤，而是“运行入口、缓存位置和运行状态”没有形成一个可核对的闭环：正式入口约定使用 `D:\\cache\\ccs\\_ablation-03`，但 fresh 启动脚本默认把结果写到 `D:\\cache\\ccs\\_ablation-03-fresh`；单个 job 开始时会留下 `running` 标记，异常退出后却没有失败记录或心跳，因此用户只能看到一个看似仍在运行、实际没有 CPU 推进的任务。大对象和 worker 的资源使用也缺少统一的运行时证据。

优化后，每次运行都必须在启动时声明唯一的运行模式和缓存根目录；缓存中的每个节点都能区分完成、失败、陈旧和正在运行；异常退出后可以安全恢复且能解释上次为何停止；正式验收只消费正式缓存，不会把隔离实验线误当成正式结果。

## 专业判断：问题在哪里

### 已确认的问题

- 正式 targets 配置指向 `_ablation-03`，而 `run-fresh-analysis.ps1` 默认指向 `_ablation-03-fresh`，两者语义不同但入口区分不够强。
- `.ablation_cached_node()` 在计算前写入 `running`，只在正常返回后写入 `complete`；异常、手动中断或进程退出不会写入 `failed`。
- `running` 状态没有 `started_at`、`updated_at`、PID、主机、配置摘要或 heartbeat，无法判断它是活跃任务还是陈旧标记。
- learning-curve 的 job 级恢复可以识别 `running` 为 miss，但没有向用户说明上次失败原因，也没有防止同一缓存根目录被错误入口再次使用的强约束。
- 当前测试覆盖了“running 应重算”，但没有覆盖异常状态落盘、陈旧运行判定、入口路径冲突和资源证据。

### 待验证假设

- 本次 `_ablation-03-fresh` 运行可能是通过 fresh launcher 启动，而不是正式 targets launcher；需要在运行记录中保留入口和参数证据后才能完全归因。
- 20:35 后的 `running` 标记可能来自 R 会话中断、内存压力或 worker 异常；现有缓存没有足够信息区分三者。
- 高内存可能来自大矩阵复制、XGBoost 临时对象或 PSOCK worker 导出；需要小规模基准和峰值记录验证，不在计划中直接假定某一个原因。

## 要达到什么目标

- 正式运行默认且唯一使用 `D:\\cache\\ccs\\_ablation-03`；fresh/benchmark 运行必须显式命名并显式传入路径。
- 任何节点异常退出都能留下可读的失败状态和错误摘要；重跑只重算失败或陈旧节点。
- 用户可以从 manifest 和运行记录回答“谁从哪里、用什么参数、运行到哪一步、为何停止”。
- 内存、CPU、worker 数和 XGBoost 线程配置有可审计记录，并能在超预算前安全降级或提前失败。
- 在不改变科学结果和输入契约的前提下，通过包检查、单元测试、targets 恢复测试和 `test/ablation-03` 串行验收。

## 改进方向

### 统一正式入口与缓存边界

把正式 targets 运行和 fresh 隔离运行拆成明确的运行模式。正式入口不再依赖脚本默认值猜测路径；启动时输出并写入 `run_id`、`mode`、`cache_root`、targets store、入口脚本和 git/CCS/renv 身份。若检测到入口模式与缓存目录不匹配，立即失败，不继续产生结果。

涉及：[test/ablation-03/_targets.yaml](../../test/ablation-03/_targets.yaml)、[test/ablation-03/targets/functions.R](../../test/ablation-03/targets/functions.R)、[test/ablation-03/scripts/run-targets-renv.ps1](../../test/ablation-03/scripts/run-targets-renv.ps1)、[test/ablation-03/scripts/run-fresh-analysis.ps1](../../test/ablation-03/scripts/run-fresh-analysis.ps1)、[test/ablation-03/README.md](../../test/ablation-03/README.md)。

普通用户的变化：运行前就能看到“这是正式线还是 fresh 线”，不会因为脚本默认参数把结果写到另一个目录。

### 让 checkpoint 状态可恢复、可解释

扩展 `.ablation_cached_node()` 的状态契约：记录 `started_at`、`updated_at`、`run_id`、PID、主机、输入/参数摘要和当前 job 信息；计算过程用 `tryCatch`/`on.exit` 写入 `failed` 或正常完成状态，并保存脱敏错误摘要。增加 stale-running 判定：只有状态仍在更新且对应进程/运行身份有效时才视为 active，否则安全标记为 stale 并重算。保留原子写入和 value hash 校验，避免把半成品当成完成结果。

涉及：[R/ablation.R](../../R/ablation.R)、[test/ablation-03/tests/32-test-node-checkpoints.R](../../test/ablation-03/tests/32-test-node-checkpoints.R) 及新增的状态恢复测试。

普通用户的变化：中断后不会再看到一个无限期的“running”；恢复时能知道上次失败在哪里，且只补算缺失 job。

### 建立资源预算和可观测性

在 learning-curve 和 PSOCK 入口统一解析 workers、总线程、内存预算，记录每个 job 的开始/结束时间、峰值工作集、worker 状态和结果大小。启动前检查配置是否会造成线程过度订阅；运行中按 job 边界释放临时对象，避免一次性保留无关结果。内存预算无法满足时应提前给出明确错误或降为串行，而不是留下不可解释的 running 状态。

涉及：[R/ablation.R](../../R/ablation.R) 的 learning-curve worker 和运行时配置、[test/ablation-03/scripts/benchmark-learning-curve.R](../../test/ablation-03/scripts/benchmark-learning-curve.R)、运行 manifest/报告输出。

普通用户的变化：可以区分“正在计算”“等待 I/O”“worker 已退出”和“已因资源预算停止”，也能根据峰值选择 workers，而不是凭任务管理器猜测。

### 补齐入口、恢复和科学等价性验证

新增最小验证矩阵：正式入口路径测试、fresh 入口隔离测试、异常后失败状态测试、陈旧状态恢复测试、同一缓存根目录并发拒绝测试、单 job 重跑测试、资源配置解析测试。完成后按项目门禁运行 R 文档/包检查、定向测试和 `ablation-03` 串行验收，确认科学输出与既有基线等价。不得把 `_ablation-03-fresh` 的结果直接搬入正式目录；如需迁移，必须先完成 manifest、输入哈希、版本和结果等价性核对。

涉及：[test/ablation-03/tests/](../../test/ablation-03/tests/)、[docs/ablation.md](../ablation.md)、[test/ablation-03/README.md](../../test/ablation-03/README.md)。

## 实施范围与顺序

1. 先冻结现有 `_ablation-03` 与 `_ablation-03-fresh`，记录两条运行线的路径、时间、输入哈希、代码版本和当前状态；不删除、不覆盖、不自动迁移缓存。
2. 先完成入口与缓存边界治理，再修改 checkpoint 状态契约；避免在路径尚未固定时继续产生新结果。
3. 完成失败状态、陈旧判定和 job 级运行记录后，再加入资源监控和预算策略。
4. 补齐测试与文档，执行定向验证；最后运行包检查、科学等价性验证和 `test/ablation-03` 串行验收。
5. 只有上述门禁全部通过，才恢复正式完整运行；是否按项目授权递增 `DESCRIPTION` patch 版本，严格遵守现有 ablation 版本门禁，不在本计划中预先改版本号。

## 如何确认完成

- 正式入口的运行记录明确显示 `mode=formal`、`cache_root=D:/cache/ccs/_ablation-03`、targets store 与入口脚本一致；fresh 入口明确显示 `mode=fresh`，且不能写入正式 store。
- 人工中断或模拟异常后，checkpoint 状态为 `failed` 或 `stale`，包含时间、运行身份和脱敏错误摘要；再次运行只重算该节点/该 job。
- 同一缓存根目录的第二个运行在启动阶段被拒绝；已有 active heartbeat 不会被误判为 stale。
- `running` 状态超过阈值且对应进程不存在时，恢复命令能安全接管，不需要人工编辑 `.rds` 文件。
- 单元测试覆盖完成、失败、损坏、陈旧和恢复路径；资源测试覆盖 workers/cores/memory 的边界和线程不超订阅。
- `Rscript -e "devtools::document()"`、`R CMD build .`、`R CMD check`、定向 `test/ablation-03/tests/*.R` 和声明的串行验收均通过；BAC verify 无新增错误。
- 正式结果只来自正式缓存根目录，报告、manifest、checkpoint 和审计记录的路径身份一致。

## 风险与待确认事项

- 需要项目负责人确认：`_ablation-03-fresh` 是否保留为独立实验线，还是今后完全禁止；计划默认保留但强制显式命名。
- 需要确认 stale 超时和资源预算的具体阈值；计划不擅自选择会影响运行时长或内存安全的数值。
- 旧 `_fresh` 结果不自动视为正式结果；若要复用，必须先做可追溯的科学等价性和输入/版本核验。
- 本计划只解决运行可靠性和边界治理，不改变 ablation 的科学定义、特征构造、统计方法或结果解释口径。
